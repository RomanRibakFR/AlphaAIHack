# Тестовые данные для моков внешних сервисов

> Задача 4 · формат v2.0
>
> Данные — `mocks/companies/` · генератор — `mocks/generate_mocks.py` · проверка — `mocks/check_mocks.py`
>
> Связанные документы: `docs/application-states.md` (путь заявки), `docs/decision-policy.md` (правила решения), модель риска — `models/pd/` (задача 2)

**Что изменилось в v2.0:** данные подогнаны под модель PD задачи 2.
- **Новые поля, которые нужны модели:** расходы по счёту по видам, остатки, крупнейшие плательщики, категория по реестру МСП, бухгалтерская отчётность юрлиц из ГИР БО.
- **PD больше не задаётся руками:** её считает настоящий `score.py` по данным мока, а проверка следит, чтобы каждая компания попадала в свою ветку.
- **Как собрать вход модели из данных мока** — раздел 5.

## 1. Как это устроено

Банк при рассмотрении заявки обращается к внешним системам — налоговой, бюро кредитных историй, платформе ЦБ — и к собственным данным о клиенте. Доступа к ним у прототипа нет (ограничение №04 кейса), поэтому их заменяет мок-сервис. Сервис пишет бэкенд, а **этот набор файлов — данные, которые он отдаёт**.

- **Один JSON-файл на тестовую компанию:** `mocks/companies/<ID>_<ИНН>.json`. Вся «правда о компании» во всех источниках сразу.
- **Мок ищет компанию по ИНН** (поле `egrul.inn`, оно же в имени файла) и отдаёт нужный раздел.
- **Раздел `meta` мок не отдаёт.** Это сценарий для проверяющих: что ввести в анкету и какой результат ожидать.
- **Все данные вымышлены.** ИНН и ОГРН начинаются с кода региона `00`, которого не существует, но контрольные цифры правильные.
- **Дата заявки и выгрузки данных — 24.10.2026.** Обороты по счёту — за 12 полных месяцев: с октября 2025 по сентябрь 2026. Это те же месяцы, что в обучающих данных модели.

## 2. Разделы файла

Структура каждого раздела повторяет реальный источник, чтобы замена мока на настоящую интеграцию меняла только адаптер, а не логику.

| Раздел | Реальный источник | Что содержит | Где используется |
|---|---|---|---|
| `meta` | — | сценарий проверки, ожидаемый результат, расчёт модели | проверяющие, `check_mocks.py`; мок не отдаёт |
| `egrul` | ЕГРЮЛ/ЕГРИП через сервис проверки контрагентов; структура по образцу ответа DaData «Организация по ИНН» | регистрация, статус, ОКВЭД, руководитель, учредители | стоп-факторы SF01, SF04, SF06; модель: возраст, отрасль |
| `fns` | сервисы ФНС: «Прозрачный бизнес», реестр МСП, сведения о задолженности, приостановления операций по счетам | налоговый режим, численность, категория МСП, долг, блокировки | стоп-фактор SF03; модель: микро/малое |
| `zsk` | платформа ЦБ «Знай своего клиента» | уровень риска по 115-ФЗ | стоп-фактор SF05 |
| `bki` | кредитный отчёт БКИ; структура по образцу отчёта НБКИ | кредиты, платежи, просрочки, строка платёжной дисциплины | стоп-фактор SF02; модель и лимит: действующие платежи |
| `bank` | внутренние данные банка по расчётному счёту (клиент действующий) | поступления и списания по видам, остатки, крупнейшие плательщики, кредиты в банке | модель: денежный поток, резерв, концентрация; лимит; сверка с анкетой |
| `financials` | ГИР БО ФНС — годовая бухгалтерская отчётность (bo.nalog.ru) | строки баланса и отчёта о финансовых результатах за 2025 год | модель юрлиц: 8 показателей отчётности |

**Общие правила формата:**
- деньги — целые рубли;
- доли — десятичные дроби (`0.17` = 17%);
- даты — `ГГГГ-ММ-ДД`, месяцы — `ГГГГ-ММ`;
- значения-списки — латиницей в верхнем регистре.

| `kpp` | 9 цифр | только у юрлица |

- даты в формате ISO, а не в миллисекундах;
- нет обёртки `suggestions[].data`;

### 3.4. `bki` — кредитный отчёт

| Поле | Смысл |
|---|---|
| `subject.type`, `.inn`, `.name` | субъект кредитной истории |
| `report_date` | дата отчёта |
| `accounts[]` | договоры, по одному объекту на договор (ниже) |
| `inquiries.last_30d`, `.last_24m` | сколько раз запрашивали кредитную историю за 30 дней и за 24 месяца |

**Поля договора (`accounts[]`):**

| Поле | Значения | Смысл |
|---|---|---|
| `contract_uid` | строка | идентификатор договора (в реальности — УИД; у нас UUID) |
| `account_type` | `BUSINESS_LOAN`, `CREDIT_LINE`, `OVERDRAFT`, `LEASING`, `CREDIT_CARD`, `CONSUMER_LOAN`, `CAR_LOAN`, `MORTGAGE` | вид обязательства |
| `relationship` | `BORROWER`, `GUARANTOR` | заёмщик или поручитель |
| `creditor_kind` | `OWN_BANK`, `OTHER_BANK`, `MFO`, `LEASING_COMPANY` | кто кредитор |
| `opened_at`, `planned_close_at`, `closed_at` | даты | открытие, плановое и фактическое закрытие |
| `status` | `ACTIVE`, `CLOSED`, `SOLD`, `WRITTEN_OFF` | действует, закрыт, долг продан, списан |
| `credit_limit`, `rate`, `currency` | рубли, доля, `RUB` | сумма или лимит, ставка, валюта |
| `outstanding` | рубли | текущая задолженность |
| `monthly_payment`, `next_payment_date` | рубли, дата | ежемесячный платёж и дата следующего |
| `overdue_amount`, `current_overdue_days` | рубли, дни | текущая просрочка |
| `overdue_counts_24m` | `d30_59`, `d60_89`, `d90_plus` | сколько было просрочек каждой длительности за 24 месяца |
| `payment_string` | строка кодов | помесячная платёжная дисциплина, последний месяц слева, до 24 месяцев |
| `collateral` | да/нет | есть ли обеспечение |

**Коды строки платёжной дисциплины** (как в отчётах НБКИ):

| Код | Значение | Код | Значение |
|---|---|---|---|
| `0` | новый договор, оценки ещё нет | `4` | просрочка 90–119 дней |
| `1` | оплата без просрочек | `5` | просрочка 120 дней и больше |
| `A` | просрочка 1–29 дней | `7` | изменения в договоре |
| `B` | просрочка 1–7 дней | `8` | погашение за счёт обеспечения |
| `C` | просрочка 8–29 дней (кириллица) | `9` | безнадёжный долг, передан на взыскание |
| `2` | просрочка 30–59 дней | `Z` | льготный период |
| `3` | просрочка 60–89 дней | `-` | нет данных |

**Важно для бэкенда:**
- **Сводки в моке нет.** Общий долг и просрочку бэкенд считает из `accounts`.
- **У ИП отчёт по физлицу.** Кредитная история ИП и физлица одна, поэтому у ИП есть и личные кредиты (`CAR_LOAN`, `CREDIT_CARD`). Они входят в действующие платежи для модели и лимита.
- **Кредиты нашего банка не удваивать.** Они есть и в `bki.accounts` (`creditor_kind = OWN_BANK`), и в `bank.own_loans` с тем же `contract_uid`. Действующие платежи считаются только по БКИ.

### 3.5. `bank` — расчётный счёт в нашем банке

| Поле | Значения | Смысл |
|---|---|---|
| `client_since` | дата | с какой даты клиент обслуживается в банке |
| `account_type` | `40702` / `40802` | счёт организации или ИП (первые пять цифр номера счёта) |
| `current_balance`, `current_balance_date` | рубли, дата | **остаток на дату заявки — денежный резерв для модели** |
| `turnover_months[]` | до 12 записей | помесячное движение по счёту (ниже) |
| `top_payers_12m[]` | `name`, `inn`, `kind`, `amount`, `share` | крупнейшие плательщики за 12 месяцев по убыванию суммы (ниже) |
| `own_loans[]` | `contract_uid`, `product`, `opened_at`, `amount`, `outstanding`, `monthly_payment`, `current_overdue_days` | действующие кредиты в нашем банке |

**Поля месяца (`turnover_months[]`):**

| Поле | Смысл |
|---|---|
| `month` | месяц `ГГГГ-ММ` |
| `credit_total` | все поступления на счёт |
| `credit_net` | **очищенные поступления — выручка бизнеса** |
| `excluded.own_transfers`, `.loans_received`, `.refunds` | что исключено из выручки: переводы со своих счетов и взносы владельца, полученные кредиты, возвраты |
| `debit_total` | все списания |
| `debit_operating` | **операционные расходы**: поставщики, зарплата, аренда, налоги |
| `debit_debt_service` | платежи по кредитам и лизингу с этого счёта |
| `debit_own_transfers` | переводы на свои счета и владельцу |
| `balance_open`, `balance_close` | остаток на начало и конец месяца |

Всегда выполняются:
- `credit_total = credit_net + own_transfers + loans_received + refunds`;
- `debit_total = debit_operating + debit_debt_service + debit_own_transfers`;
- `balance_close = balance_open + credit_total − debit_total`; остаток на начало месяца равен остатку на конец прошлого.

**Плательщики (`top_payers_12m[]`):**
- `kind = LEGAL` — компании-покупатели, у них есть ИНН.
- `kind = RETAIL_ACQUIRING` — суммарные оплаты физлиц картами и через СБП. Это тысячи разных людей, а не один покупатель, поэтому **в долю крупнейшего покупателя эта строка не входит**.
- `share` = `amount` / сумма `credit_net` за 12 месяцев.

Если клиент обслуживается меньше года, месяцев меньше 12 (компания C14 — 7 месяцев).

### 3.6. `financials` — годовая отчётность из ГИР БО

У ИП отчётности нет: `financials = null`. У юрлица, зарегистрированного в текущем году, её тоже ещё нет (C14).

|---|---|---|
| `source` | `GIR_BO` | государственный информационный ресурс бухгалтерской отчётности ФНС |
| `year` | `2025` | отчётный год (сдаётся до 31 марта следующего года) |
| `report_form` | `FULL` / `SIMPLIFIED` | полная или упрощённая форма; микропредприятия сдают упрощённую |
| `unit` | `RUB` | рубли (в самом ГИР БО — тысячи рублей; здесь уже пересчитано, суммы кратны 1000) |
| `lines` | коды строк → суммы | строки отчётности (ниже) |
| `submitted_at` | дата | когда сдана |

| Строка | Что это |
|---|---|
| `1600` | баланс (всего активов) |
| `1300` | капитал и резервы (может быть отрицательным) |
| `1200` | оборотные активы |
| `1500` | краткосрочные обязательства |
| `2110` | выручка |
| `2120` | себестоимость продаж (полная форма) или расходы по обычной деятельности (упрощённая), **по модулю**; `null` — строка не заполнена |
| `2400` | чистая прибыль (отрицательная — убыток) |

### 3.7. `meta` — сценарий проверки

| Поле | Смысл |
|---|---|
| `id`, `title` | номер и краткое описание компании |
| `scenario.product`, `.amount`, `.term_months`, `.purpose` | что ввести в анкету |
| `scenario.declared_revenue_12m` | выручка за 12 месяцев, которую клиент указывает в анкете |
| `scenario.collateral` | залог (только `INVESTMENT`): вид, описание, стоимость |
| `scenario.document_on_request` | что загрузить, когда банк запросит выписку: тип и сумма поступлений по ней |
| `expected.scenario_id`, `.path` | сценарий и переходы из `docs/application-states.md` |
| `expected.outcome`, `.reason`, `.grade` | задуманный исход автоматической обработки, его причина и класс риска |
| `expected.note` | пояснение, если есть |
| `expected.model` | **расчёт настоящей моделью** на предлагаемых условиях: `segment`, `model_id`, `pd`, `grade`, `lgd`, `product_pd_max`, `inputs` (точный вход `score.py`), `top_risk_factors`, `clipped_features`; `null`, если до модели заявка не дошла |
| `expected.offer` | предложение, которое должна сформировать политика: тип, сумма, срок, ставка, платёж, что ограничило лимит |

Значения `outcome`: `AUTO_APPROVED`, `COUNTER_OFFER`, `MANUAL_REVIEW`, `REJECTED`, `INFO_REQUESTED`. Коды `reason` — из `docs/decision-policy.md`: стоп-факторы `SF01`–`SF06`, ручная проверка `M1`–`M8`, `TERM_EXTENDED`, `AMOUNT_REDUCED`, `HIGH_RISK`, `NO_VIABLE_OFFER`.

`expected.model` и `expected.offer` пишет генератор, а `check_mocks.py` каждый раз пересчитывает их заново и сравнивает. Если в данные или модель внесли изменение, проверка покажет, что именно разошлось.

## 4. Поведение мока

**Маршруты** — каждый отдаёт свой раздел без служебных полей:

| Маршрут | Раздел | Особенности |
|---|---|---|
| `GET /egrul/{inn}` | `egrul` | |
| `GET /fns/{inn}` | `fns` | |
| `GET /zsk/{inn}` | `zsk` | |
| `GET /bki/{inn}` | `bki` | у C17 — 503 |
| `GET /bank/{inn}` | `bank` | |
| `GET /gir-bo/{inn}` | `financials` | 404, если `financials = null` (ИП или компания без отчётности) |

- Неизвестный ИНН → 404, как у настоящего сервиса.
- Раздел `meta` не отдаётся.
- Служебное поле `_mock` может быть в любом разделе. Мок его не отдаёт, а выполняет:

```json
"_mock": {"mode": "unavailable", "delay_ms": 1500}
```

| `mode` | Что делает мок |
|---|---|
| `ok` (по умолчанию) | отдаёт раздел |
| `unavailable` | отвечает ошибкой 503 — источник недоступен |
| `timeout` | не отвечает дольше таймаута бэкенда |
| `not_found` | отвечает 404 — сведений нет |

Задержки по умолчанию (предложение): ЕГРЮЛ ~300 мс, БКИ ~1500 мс. Тогда в кабинете видно, как идут подшаги «проверяем данные → смотрим кредитную историю».

## 5. Как собрать вход модели из данных мока

Модель задачи 2 (`models/pd/<ip|ul>/score.py`) принимает словарь «сырых» входов и сама считает из них признаки. Бэкенд собирает этот словарь так. Эталонная реализация — функция `model_inputs` в `mocks/check_mocks.py`, результат для каждой компании лежит в `meta.expected.model.inputs`.

| Вход `score.py` | Откуда в данных мока |
|---|---|
| `business_age_years` | (дата заявки − `egrul.state.registration_date`) в днях / 365,25 |
| `msp_category` | `fns.msp_register.category` строчными: `micro` / `small` |
| `okved_main` | `egrul.okved` |
| `monthly_receipts_rub` | среднее `bank.turnover_months[].credit_net` |
| `monthly_operating_outflows_rub` | среднее `bank.turnover_months[].debit_operating` |
| `existing_monthly_debt_service_rub` | сумма `monthly_payment` по `bki.accounts` со `status = ACTIVE` и `relationship = BORROWER` |
| `new_monthly_debt_service_rub` | аннуитетный платёж по запрошенной (или подобранной) сумме и сроку **по потолку ставки продукта** — `docs/decision-policy.md`, раздел 5.3 |
| `receipts_growth_6m_pct` | (среднее `credit_net` за последние 3 месяца / среднее за предыдущие 3 − 1) × 100 |
| `receipts_cv_pct` | стандартное отклонение `credit_net` по месяцам (по генеральной совокупности, ddof = 0) / среднее × 100 |
| `cash_reserve_rub` | `bank.current_balance` |
| `largest_customer_share_pct` | наибольшая `amount` среди `top_payers_12m` с `kind ≠ RETAIL_ACQUIRING` / сумма `credit_net` × 100; если таких нет — 0 |
| только юрлица: `unit` | `"rub"` |

| `assets`, `equity`, `current_assets`, `current_liabilities` | `financials.lines` `1600`, `1300`, `1200`, `1500` |
| `revenue`, `net_profit` | `financials.lines` `2110`, `2400` |
| `ordinary_expenses` | `financials.lines` `2120`; `null` передаётся как `null` — модель сама подставит медиану и поставит флаг |

**Какую модель вызывать:** `egrul.type = INDIVIDUAL` → `models/pd/ip/model.json`, `LEGAL` → `models/pd/ul/model.json`. Файл `score.py` у обеих моделей одинаковый.

**Пример** (Python, только стандартная библиотека):

```python
import json, importlib.util
spec = importlib.util.spec_from_file_location("pd_score", "models/pd/ul/score.py")
pd_score = importlib.util.module_from_spec(spec); spec.loader.exec_module(pd_score)
model = json.load(open("models/pd/ul/model.json", encoding="utf-8"))
result = pd_score.score(inputs, model)   # inputs — словарь по таблице выше
result["pd_probability"]                  # вероятность дефолта
result["contribution_details"]            # вклад каждого признака → объяснение решения
result["clipping_warnings"]               # значения вне диапазона обучения
```

Если данных не хватает (например, у юрлица нет отчётности), `score` возвращает `status = REQUEST_DATA` со списком ошибок — по политике заявка уходит к специалисту (M6).

## 7. Как менять и добавлять компании

- **Основной способ:** поправить компанию в списке `COMPANIES` в `mocks/generate_mocks.py`, запустить `python mocks/generate_mocks.py`, затем `python mocks/check_mocks.py`. Все строки должны быть с ✓.
- **Ручная правка JSON** допустима, но после неё генератор не запускать — он перезапишет файлы. Проверку запускать в любом случае: если изменились данные, она покажет новую PD и где разошлось.
- **Новая компания:** скопировать похожую запись, дать новый `id`. Генератор сам выдаст ИНН и ОГРН с правильными контрольными цифрами.
- **Если переобучили модель** (новый `model.json`) или поменяли политику, запустить генератор и проверку. Проверка покажет компании, которые ушли из своей ветки; их параметры (обычно `reserve_m`) нужно подстроить.

## 9. Допущения

- Все компании, люди, адреса, номера договоров и решений вымышлены.
- `state.code` не заполняется: для процесса достаточно `state.status`.
- `rate` в договоре БКИ — процентная ставка; в реальных отчётах по потребительским кредитам вместо неё указывается полная стоимость кредита.
- Выписка из другого банка не разбирается: используется сумма, которую указал клиент.
- Категория МСП определяется по численности и выручке из отчётности; в реальном реестре учитывается ещё и структура участников.
- Дата заявки зафиксирована (24.10.2026), чтобы возраст бизнеса и ожидаемые исходы не менялись со временем. В бэкенде её стоит брать из конфигурации, а не из системных часов.
