# Тестовые данные для моков внешних сервисов

> Задача 4 · формат v1.0
>
> Данные — `mocks/companies/` · генератор — `mocks/generate_mocks.py` · проверка — `mocks/check_mocks.py`
>
> Связанные документы: `docs/application-states.md` (путь заявки), `docs/decision-policy.md` (правила решения)

## 1. Как это устроено

Банк при рассмотрении заявки обращается к внешним системам: налоговой, бюро кредитных историй, платформе ЦБ — и к собственным данным о клиенте. Доступа к ним у прототипа нет (ограничение №04 кейса), поэтому их заменяет мок-сервис. Сервис пишет бэкенд, а **этот набор файлов — данные, которые он отдаёт**.

- **Один JSON-файл на тестовую компанию:** `mocks/companies/<ID>_<ИНН>.json`. В файле вся «правда о компании» во всех источниках сразу — её легко прочитать и проверить целиком.
- **Мок ищет компанию по ИНН** (поле `egrul.inn`, оно же в имени файла) и отдаёт нужный раздел.
- **Раздел `meta` мок не отдаёт.** Это сценарий для проверяющих: что ввести в анкету и какой результат ожидать.
- **Все данные вымышлены.** ИНН и ОГРН начинаются с кода региона `00`, которого не существует, поэтому не совпадут с реальной компанией. При этом контрольные цифры правильные, и номера проходят любую валидацию формата.
- **Дата выгрузки данных — 24.10.2026.** Обороты по счёту — за 12 полных месяцев: с октября 2025 по сентябрь 2026.

## 2. Разделы файла

Структура каждого раздела повторяет реальный источник, чтобы замена мока на настоящую интеграцию меняла только адаптер, а не логику.

| Раздел | Реальный источник | Что содержит | Где используется |
|---|---|---|---|
| `meta` | — | сценарий проверки и ожидаемый результат | проверяющие, `check_mocks.py`; мок не отдаёт |
| `egrul` | ЕГРЮЛ/ЕГРИП через сервис проверки контрагентов; структура — по образцу ответа DaData «Организация по ИНН» | регистрация, статус, ОКВЭД, руководитель, учредители | стоп-факторы SF01, SF04, SF06; признак F1 |
| `fns` | сервисы ФНС: «Прозрачный бизнес», сведения о задолженности, сервис приостановлений операций по счетам | налоговый режим, численность, долг, блокировки счетов | стоп-фактор SF03 |
| `zsk` | платформа ЦБ «Знай своего клиента» | уровень риска по 115-ФЗ | стоп-фактор SF05 |
| `bki` | кредитный отчёт бюро кредитных историй; структура — по образцу отчёта НБКИ | кредиты, просрочки, строка платёжной дисциплины, запросы | стоп-фактор SF02; признаки F4, F5 |
| `bank` | внутренние данные банка: клиент действующий | очищенные обороты по счёту, кредиты в нашем банке | признаки F2, F3; лимит; сверка с анкетой |

**Общие правила формата:**
- деньги — целые рубли;
- доли — десятичные дроби (`0.17` = 17%);
- даты — `ГГГГ-ММ-ДД`, месяцы — `ГГГГ-ММ`;
- значения-списки — латиницей в верхнем регистре.

## 3. Поля

### 3.1. `egrul` — ЕГРЮЛ / ЕГРИП

| Поле | Значения | Смысл |
|---|---|---|
| `type` | `LEGAL` / `INDIVIDUAL` | юрлицо или ИП |
| `inn` | 10 цифр (юрлицо), 12 (ИП) | ИНН, ключ поиска |
| `kpp` | 9 цифр | КПП; только у юрлица |
| `ogrn` | 13 цифр (ОГРН), 15 (ОГРНИП) | регистрационный номер |
| `name.full_with_opf`, `name.short_with_opf` | строка | полное и краткое наименование |
| `fio.surname`, `fio.name`, `fio.patronymic` | строка | ФИО; только у ИП |
| `opf.code`, `opf.short` | `12300` ООО, `50102` ИП | организационно-правовая форма по ОКОПФ |
| `state.status` | `ACTIVE`, `LIQUIDATING`, `LIQUIDATED`, `BANKRUPT`, `REORGANIZING` | статус: действует, ликвидируется, ликвидирована, банкротство, реорганизация |
| `state.code` | `null` | детальный код статуса по справочнику ФНС; в моке не заполняется |
| `state.registration_date` | дата | дата регистрации, из неё считается срок ведения бизнеса |
| `state.liquidation_date` | дата или `null` | дата ликвидации |
| `state.actuality_date` | дата | на какую дату актуальны сведения |
| `okved`, `okved_name` | код и название | основной вид деятельности |
| `management.name`, `.inn`, `.post`, `.start_date` | — | руководитель и с какой даты; только у юрлица |
| `founders[]` | `name`, `inn`, `type` (`PHYSICAL` / `LEGAL`), `share` (`{"type": "PERCENT", "value": 100}`), `start_date` | учредители и доли; только у юрлица |
| `address.value` | строка | адрес; у ИП — только населённый пункт, как в открытых данных ЕГРИП |
| `invalid` | `true` / `null` | отметка о недостоверности сведений |

**Отличия от ответа DaData:**
- даты в формате ISO, а не в миллисекундах;
- нет обёртки `suggestions[].data`;
- добавлено `okved_name`;
- оставлены только поля, нужные процессу.

### 3.2. `fns` — сервисы ФНС

| Поле | Значения | Смысл |
|---|---|---|
| `tax_regime` | `OSNO`, `USN`, `PSN`, `AUSN`, `ESHN` | общая система, упрощёнка, патент, АУСН, ЕСХН |
| `employee_count`, `employee_count_year` | число, год | среднесписочная численность за год |
| `tax_debt.has_debt`, `.amount`, `.as_of` | да/нет, рубли, дата | задолженность по налогам, пеням и штрафам |
| `account_suspensions[]` | `decision_number`, `decision_date`, `reason_code`, `bank` (`OWN_BANK` / `OTHER_BANK`), `active` | решения налоговой о приостановлении операций по счетам |
| `no_reporting_over_year` | да/нет | компания не сдаёт отчётность больше года |

Коды `reason_code` — как в сервисе ФНС: `1` — взыскание задолженности, `2` — непредставление декларации.

Упрощение: в реальности факт долга даёт справка по сальдо единого налогового счёта (без суммы), сумму недоимки — «Прозрачный бизнес», а приостановления запрашиваются по ИНН и БИК банка. В моке всё собрано в одном разделе.

### 3.3. `zsk` — платформа «Знай своего клиента»

| Поле | Значения | Смысл |
|---|---|---|
| `risk_level` | `GREEN`, `YELLOW`, `RED` | низкий, средний, высокий уровень риска |
| `assigned_at` | дата | когда присвоен |

### 3.4. `bki` — кредитный отчёт

| Поле | Смысл |
|---|---|
| `subject.type`, `.inn`, `.name` | субъект кредитной истории |
| `report_date` | дата отчёта |
| `accounts[]` | договоры, по одному объекту на договор (ниже) |
| `inquiries.last_30d`, `.last_24m` | сколько раз кредитную историю запрашивали за 30 дней и за 24 месяца |

**Поля договора (`accounts[]`):**

| Поле | Значения | Смысл |
|---|---|---|
| `contract_uid` | строка | уникальный идентификатор договора (в реальности — УИД с контрольным символом; у нас UUID) |
| `account_type` | `BUSINESS_LOAN`, `CREDIT_LINE`, `OVERDRAFT`, `LEASING`, `CREDIT_CARD`, `CONSUMER_LOAN`, `CAR_LOAN`, `MORTGAGE` | вид обязательства |
| `relationship` | `BORROWER`, `GUARANTOR` | заёмщик или поручитель |
| `creditor_kind` | `OWN_BANK`, `OTHER_BANK`, `MFO`, `LEASING_COMPANY` | кто кредитор |
| `opened_at`, `planned_close_at`, `closed_at` | даты | открытие, плановое и фактическое закрытие |
| `status` | `ACTIVE`, `CLOSED`, `SOLD`, `WRITTEN_OFF` | действует, закрыт, долг продан, списан |
| `credit_limit`, `rate`, `currency` | рубли, доля, `RUB` | сумма или лимит, ставка, валюта |
| `outstanding` | рубли | текущая задолженность |
| `monthly_payment`, `next_payment_date` | рубли, дата | ежемесячный платёж и дата следующего |
| `overdue_amount`, `current_overdue_days` | рубли, дни | текущая просрочка |
| `overdue_counts_24m` | `d30_59`, `d60_89`, `d90_plus` | сколько было просрочек каждой длительности за 24 месяца |
| `payment_string` | строка кодов | помесячная платёжная дисциплина, последний месяц слева, до 24 месяцев |
| `collateral` | да/нет | есть ли обеспечение |

**Коды строки платёжной дисциплины** (как в отчётах НБКИ):

| Код | Значение | Код | Значение |
|---|---|---|---|
| `0` | новый договор, оценки ещё нет | `4` | просрочка 90–119 дней |
| `1` | оплата без просрочек | `5` | просрочка 120 дней и больше |
| `A` | просрочка 1–29 дней | `7` | изменения в договоре |
| `B` | просрочка 1–7 дней | `8` | погашение за счёт обеспечения |
| `C` | просрочка 8–29 дней (кириллица) | `9` | безнадёжный долг, передан на взыскание |
| `2` | просрочка 30–59 дней | `Z` | льготный период |
| `3` | просрочка 60–89 дней | `-` | нет данных |

**Важно для бэкенда:**
- **Сводки в моке нет.** В реальном отчёте есть сводка (сколько договоров, общий долг, общая просрочка). Её считает бэкенд из `accounts`: если хранить сводку отдельно, она рано или поздно разойдётся с договорами.
- **У ИП отчёт по физлицу.** Кредитная история ИП и физлица одна и та же, поэтому у ИП в отчёте есть и личные кредиты (`CAR_LOAN`, `CREDIT_CARD` и т. п.). Они учитываются в долговой нагрузке.
- **Кредиты нашего банка не удваивать.** Они есть и в отчёте БКИ (`creditor_kind = OWN_BANK`), и в разделе `bank.own_loans` с тем же `contract_uid`. Долговая нагрузка считается только по БКИ.

### 3.5. `bank` — внутренние данные банка

| Поле | Значения | Смысл |
|---|---|---|
| `client_since` | дата | с какой даты клиент обслуживается в банке |
| `account_type` | `40702` / `40802` | счёт коммерческой организации или ИП (первые пять цифр номера расчётного счёта) |
| `turnover_months[]` | до 12 записей | помесячные обороты по расчётному счёту (ниже) |
| `own_loans[]` | `contract_uid`, `product`, `opened_at`, `amount`, `outstanding`, `monthly_payment`, `current_overdue_days` | действующие кредиты в нашем банке |

**Поля месяца (`turnover_months[]`):**

| Поле | Смысл |
|---|---|
| `month` | месяц `ГГГГ-ММ` |
| `credit_total` | все поступления на счёт |
| `credit_net` | **очищенные** поступления, то есть выручка бизнеса |
| `excluded.own_transfers`, `.loans_received`, `.refunds` | что исключено: переводы между своими счетами, полученные кредиты и займы, возвраты |
| `debit_total` | все списания |
| `avg_balance` | средний остаток |

Всегда выполняется `credit_total = credit_net + own_transfers + loans_received + refunds`.

Лимиты и признаки модели считаются **только по очищенным оборотам**. Переводы самому себе и полученные кредиты — не выручка, иначе компания могла бы «нагнать» обороты.

Если клиент обслуживается меньше года, месяцев меньше 12 (компания C14 — 7 месяцев).

### 3.6. `meta` — сценарий проверки

| Поле | Смысл |
|---|---|
| `id`, `title` | номер и краткое описание компании |
| `scenario.product`, `.amount`, `.term_months`, `.purpose` | что ввести в анкету: продукт, сумма, срок, цель |
| `scenario.declared_revenue_12m` | выручка за 12 месяцев, которую клиент указывает в анкете |
| `scenario.collateral` | залог (только для `INVESTMENT`): вид, описание, стоимость |
| `scenario.documents_at_submit` | какие документы приложить при отправке (`financial_statements` — отчётность) |
| `scenario.document_on_request` | что загрузить, когда банк запросит документ: тип и сумма оборотов по выписке |
| `expected.scenario_id`, `.path` | сценарий и переходы из `docs/application-states.md` |
| `expected.outcome`, `.reason` | ожидаемый исход автоматической обработки и его причина |
| `expected.assumed_grade`, `.assumed_pd` | в какой класс риска должна попасть компания (допущение для модели задачи 2) |
| `expected.features` | признаки F1–F6, посчитанные из данных файла |
| `expected.note` | пояснение, если есть |

Значения `outcome`: `AUTO_APPROVED`, `COUNTER_OFFER`, `MANUAL_REVIEW`, `REJECTED`, `INFO_REQUESTED`.

Коды `reason` — из `docs/decision-policy.md`: стоп-факторы `SF01`–`SF06`, признаки ручной проверки `M1`–`M5`, `TERM_EXTENDED`, `AMOUNT_REDUCED`, `HIGH_RISK`, `NO_VIABLE_OFFER`.

## 4. Поведение мока

Любой раздел может содержать служебное поле `_mock`. Мок его не отдаёт, а выполняет:

```json
"_mock": {"mode": "unavailable", "delay_ms": 1500}
```

| `mode` | Что делает мок |
|---|---|
| `ok` (по умолчанию) | отдаёт раздел |
| `unavailable` | отвечает ошибкой 503 — источник недоступен |
| `timeout` | не отвечает дольше таймаута бэкенда |
| `not_found` | отвечает 404 — сведений нет |

**Предложения для сервиса моков:**
- Задержки по умолчанию, как у живых сервисов: ЕГРЮЛ ~300 мс, БКИ ~1500 мс. Тогда в личном кабинете видно, как меняются подшаги «Проверяем данные компании → смотрим кредитную историю».
- Если ИНН нет в данных — 404, как у настоящего сервиса.
- Маршруты: `GET /egrul/{inn}`, `/fns/{inn}`, `/zsk/{inn}`, `/bki/{inn}`, `/bank/{inn}` — каждый отдаёт свой раздел без `_mock`.

## 6. Как менять и добавлять компании

- **Основной способ:** поправить описание компании в списке `COMPANIES` в `mocks/generate_mocks.py`, запустить генератор, затем `python mocks/check_mocks.py`. Все строки должны быть с ✓.
- **Можно править JSON вручную,** но тогда генератор больше не запускать: он перезапишет файлы. Проверку запускать в любом случае.
- **Новая компания:** скопировать похожую запись, дать новый `id`. Генератор сам выдаст уникальный ИНН и ОГРН с правильными контрольными цифрами.
- **Если поменялись правила** в `config/decision_policy.yaml`, проверка покажет, какие компании ушли из своей ветки.
