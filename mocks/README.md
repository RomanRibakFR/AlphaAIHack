# Моки внешних сервисов — тестовые данные

Данные для мок-сервиса: 17 вымышленных компаний, по одной на каждую ветку пути заявки. Сам сервис пишет бэкенд; здесь — то, что он отдаёт.

**Версия 2.0:** данные подогнаны под модель PD задачи 2. PD каждой компании считает настоящий `score.py`, а не задаётся руками.

Полное описание полей — `docs/mocks-format.md`.

## Что нужно от мок-сервиса

1. **Загрузка.** При старте прочитать все `mocks/companies/*.json`, построить индекс по `egrul.inn`.
2. **Маршруты** — каждый отдаёт свой раздел файла:
   - `GET /egrul/{inn}` → `egrul`
   - `GET /fns/{inn}` → `fns`
   - `GET /zsk/{inn}` → `zsk`
   - `GET /bki/{inn}` → `bki`
   - `GET /bank/{inn}` → `bank`
   - `GET /gir-bo/{inn}` → `financials` (404, если `null`: у ИП отчётности нет)
3. **Не отдавать** раздел `meta` и служебное поле `_mock`.
4. **Поведение `_mock`.** Поле может быть в любом разделе, сейчас есть только у C17 в `bki`:
   - `unavailable` — ответить 503;
   - `timeout` — не отвечать дольше таймаута бэкенда;
   - `not_found` — ответить 404;
   - `delay_ms` — задержка перед ответом.
5. **Неизвестный ИНН** — 404.
6. **Задержки по умолчанию** (предложение): ЕГРЮЛ ~300 мс, БКИ ~1500 мс — чтобы в кабинете было видно, как идут подшаги «проверяем данные → смотрим кредитную историю».

## Как вызвать модель

Вход модели собирается из данных мока по таблице в `docs/mocks-format.md`, раздел 5. Для каждой компании готовый вход лежит в `meta.expected.model.inputs` — удобно для автотестов.

```python
result = pd_score.score(inputs, model)   # models/pd/<ip|ul>/score.py и model.json
result["pd_probability"]                  # PD; класс и исход — по docs/decision-policy.md
```

## Важное для логики бэкенда

- **Выручка — только `credit_net`** (очищенные поступления). `credit_total` включает переводы самому себе и полученные кредиты.
- **Операционные расходы — `debit_operating`.** Платежи по кредитам и переводы себе в них не входят.
- **Резерв для модели — `bank.current_balance`** (остаток на дату заявки).
- **Доля крупнейшего покупателя — без строки `RETAIL_ACQUIRING`.** Оплаты физлиц картами — это тысячи людей, а не один покупатель.
- **Действующие платежи — только по БКИ.** Кредиты нашего банка есть и в `bki.accounts` (`OWN_BANK`), и в `bank.own_loans` с тем же `contract_uid` — не удваивать.
- **У ИП в БКИ есть личные кредиты** (автокредит, кредитная карта): история ИП и физлица одна, они входят в нагрузку.
- **Платёж по новому кредиту для модели — по потолку ставки продукта**, а клиенту показывается платёж по его фактической ставке (`docs/decision-policy.md`, раздел 5.3).
- **Дата заявки зафиксирована — 24.10.2026** (`config/decision_policy.yaml` → `model.application_date`). Возраст бизнеса считать от неё, иначе со временем ожидаемые исходы сдвинутся.
- **Деньги — целые рубли, доли — дроби** (`0.17` = 17%), даты — `ГГГГ-ММ-ДД`.

## Проверка данных

Python 3.10+ и PyYAML:

```bash
pip install pyyaml
python mocks/check_mocks.py
```

Должно быть 17 строк с ✓ и `ошибок: 0`. В каждой строке — исход, PD по модели, класс риска и предложение.

Проверить сам мок-сервис после запуска:

```bash
npx newman run postman/mock-sources.postman_collection.json --env-var mocks_url=http://localhost:8001
```

Скрипт — инструмент проверки данных, а не код продукта: политика в нём упрощённо повторяет `docs/decision-policy.md`. Но функции `model_inputs` и `simulate` можно использовать как эталон: бэкенд на тех же данных должен получить те же числа.

## Как менять данные

- **Основной способ:** поправить компанию в списке `COMPANIES` в `generate_mocks.py` → `python mocks/generate_mocks.py` → `python mocks/check_mocks.py`.
- **Ручная правка JSON** допустима, но после неё генератор не запускать — он перезапишет файлы.
- **Если задача 2 переобучила модель** — положить новые `model.json` в `models/pd/`, запустить генератор и проверку.
- **По вопросам данных** — к Аскару (задача 4).
